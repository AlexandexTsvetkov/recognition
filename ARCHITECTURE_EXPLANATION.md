# Объяснение архитектуры микросервисов

## Почему такая архитектура?

### Проблемы монолитной архитектуры:
1. **Невозможность независимого масштабирования** - весь сервис масштабируется целиком
2. **Единая точка отказа** - падение одного компонента останавливает всю систему
3. **Блокирующая обработка** - клиент ждет завершения распознавания
4. **Сложность горизонтального масштабирования** - сложно добавить больше обработчиков

### Решение через микросервисы:

## 1. API Gateway (Порт 8080)
**Зачем**: Быстрый ответ клиенту, не блокируем его на время обработки

**Что делает**:
- Принимает запрос с аудио файлом
- Валидирует данные
- Отправляет задачу в Request Service
- **Сразу возвращает taskId** клиенту (не ждет обработки!)
- Клиент может проверить статус позже через GET /tasks/{taskId}

**Преимущества**:
- Клиент не ждет долгую обработку
- Можно обрабатывать много запросов параллельно
- Легко добавить rate limiting, аутентификацию

## 2. Request Service (Порт 8082)
**Зачем**: Управление жизненным циклом задач, сохранение метаданных

**Что делает**:
- Создает задачу в БД со статусом PENDING
- Отправляет задачу в Kafka топик `recognition-tasks`
- Слушает результаты из Kafka топика `recognition-results`
- Обновляет статус задачи в БД

**Преимущества**:
- Метаданные сохраняются даже если обработка упадет
- Можно отслеживать все задачи
- Легко добавить retry механизм

## 3. Processing Service (Порт 8083)
**Зачем**: Обработка распознавания речи - самая тяжелая часть

**Что делает**:
- Слушает задачи из Kafka топика `recognition-tasks`
- Взаимодействует с Yandex SpeechKit через gRPC
- Обрабатывает результаты
- Отправляет результаты в Kafka топик `recognition-results`

**Преимущества**:
- **Можно запустить много экземпляров** для параллельной обработки
- Каждый экземпляр обрабатывает задачи независимо
- Circuit Breaker защищает от сбоев SpeechKit
- Rate Limiter защищает от перегрузки API

**Масштабирование**: 
- При высокой нагрузке просто запускаем больше экземпляров
- Kafka автоматически распределяет задачи между экземплярами

## 4. Result Service (Порт 8084)
**Зачем**: Сохранение результатов для долгосрочного хранения

**Что делает**:
- Слушает результаты из Kafka топика `recognition-results`
- Сохраняет результаты в БД
- Обеспечивает персистентность данных

**Преимущества**:
- Результаты не теряются
- Можно делать аналитику, статистику
- Можно добавить поиск по результатам

## Поток данных (пример)

```
1. Клиент отправляет аудио → API Gateway
   ↓
2. API Gateway → Request Service (создает задачу)
   ↓
3. Request Service сохраняет в БД (status: PENDING)
   ↓
4. Request Service отправляет в Kafka (topic: recognition-tasks)
   ↓
5. API Gateway возвращает taskId клиенту (быстро!)
   ↓
6. Processing Service получает задачу из Kafka
   ↓
7. Processing Service → Yandex SpeechKit (gRPC)
   ↓
8. Processing Service получает результат
   ↓
9. Processing Service отправляет в Kafka (topic: recognition-results)
   ↓
10. Request Service обновляет статус в БД (status: SUCCESS)
   ↓
11. Result Service сохраняет результат в БД
   ↓
12. Клиент проверяет статус через GET /tasks/{taskId}
```

## Почему Kafka?

1. **Асинхронность**: Задачи обрабатываются асинхронно, клиент не ждет
2. **Надежность**: Сообщения не теряются, можно повторить обработку
3. **Масштабируемость**: Легко добавить больше обработчиков
4. **Порядок обработки**: Можно гарантировать порядок через партиционирование
5. **Буферизация**: Выдерживает пиковые нагрузки

## Почему PostgreSQL?

1. **Надежность**: ACID транзакции
2. **Производительность**: R2DBC для неблокирующих операций
3. **Масштабируемость**: Можно настроить репликацию
4. **Гибкость**: Легко добавить индексы, аналитику

## Масштабирование в production

### При низкой нагрузке:
- 1 экземпляр каждого сервиса
- 1 Kafka брокер
- 1 PostgreSQL instance

### При высокой нагрузке:
- API Gateway: 2-3 экземпляра (за балансировщиком)
- Request Service: 2-3 экземпляра
- **Processing Service: 5-10 экземпляров** (самый важный для масштабирования!)
- Result Service: 2-3 экземпляра
- Kafka: 3 брокера (кластер)
- PostgreSQL: Master + 2 Replicas

### Автомасштабирование:
- Можно настроить Kubernetes HPA для автоматического масштабирования Processing Service
- При росте очереди в Kafka → больше экземпляров Processing Service

## Отказоустойчивость

1. **Circuit Breaker**: Защита от сбоев SpeechKit
2. **Retry**: Автоматические повторы при ошибках
3. **Rate Limiter**: Защита от перегрузки API
4. **Kafka Replication**: Сообщения не теряются
5. **Database Replication**: Данные не теряются

## Мониторинг

Все сервисы предоставляют:
- Health checks
- Metrics (Prometheus)
- Логирование

Можно настроить:
- Grafana для визуализации метрик
- Alerting при проблемах
- Distributed tracing для отслеживания запросов

## Итог

Эта архитектура обеспечивает:
✅ Высокую доступность
✅ Горизонтальное масштабирование
✅ Отказоустойчивость
✅ Производительность
✅ Легкость развертывания и мониторинга
